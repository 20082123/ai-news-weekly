# AI Signal Agent 产品总纲

这份文档回答一个问题：**我们到底在做什么，什么结果才算有价值。**

如果后续设计、代码或数据源与这里冲突，应先更新并确认本文件，不能让已经实现的技术反过来改变产品目标。

## 1. North Star

> **AI Signal Agent 以受众为先、与来源无关。它不追所有 AI 新闻，只追那些会实质改变目标用户工作、创作、决策或花钱方式的 AI 变化，并告诉他现在应该做什么。**

GitHub、Official、Web、X、Reddit 都只是传感器，不是产品本身，也不是产品分类体系。

## 2. 第一用户与目标受众

### 第一用户

第一版只服务项目所有者本人。先证明它能稳定帮助本人发现、研究和采用内容，再考虑多用户与商业化。

### 第一批内容受众

需要亲自使用 AI 完成工作的年轻知识工作者和独立创作者。

他们通常没有专门团队替自己筛选 AI 变化，需要自己判断：

- 这次变化是否真的与我的任务有关；
- 值不值得现在投入时间或付费；
- 官方宣传与真实使用之间有什么差距；
- 如果要试，今天可以从哪一步开始。

“程序员、产品、运营、市场、自由职业者、小团队负责人”可以是具体子群体，但第一版不为每个职业分别建设一套产品。

## 3. 产品必须回答的三个问题

每一条进入系统的 AI Signal 都必须逐步回答：

1. **What changed?** 发生了什么具体变化？
2. **Why should this audience care?** 它为什么与某类人的具体工作任务有关？
3. **What should they do?** 现在应该采用、测试、观察，还是忽略？

只回答“这是一个什么仓库/产品”的内容，不是合格的最终 Signal。

### 3.1 “AI Signal”在本项目中的定义

> **AI Signal = 已确认的 AI 变化（Event）+ 对一个具体受众任务的潜在影响 + 当前证据状态 + 建议的下一步行动。**

Event 只说明“发生了什么”；AI Signal 进一步说明“为什么这个人应当在意、现在该做什么”。
Signal Card 是 AI Signal 的短形式展示，Research Dossier 是它的深度研究载体。

历史 2B 数据库里名为 `signal` 的记录只是旧 schema 对 GitHub 仓库快照的派生对象，
不等于这里的产品级 AI Signal。

## 4. 第一版用户可见输出

产品输出分成四层，不能互相冒充：

### 4.1 Signal Card：快速判断

每天最多提供 3 条高质量信号；没有合格信号时可以输出 0 条，绝不凑数。

一张卡片至少说明：具体变化、第一方来源、可能影响的人和任务、目前未知的信息，以及建议继续研究还是忽略。

### 4.2 Research Dossier：负责任地研究

每周目标形成 2 份深挖档案。档案围绕“事件及其工作影响”组织，而不是围绕某个网页或仓库组织。

档案应分开记录：事实、官方宣称、独立证据、用户案例、本人实测、反例与未知项。

### 4.3 Editorial Decision：决定下一步

每份 Dossier 最终只能进入以下一种状态：

- `ready_to_write`：证据足以负责任地报道“发生了什么、为何值得关注”；
- `needs_testing`：若要声称好用、提效或适合某任务，仍需本人测试；
- `watch`：目前可能重要，但证据或时机不足；
- `reject`：与目标受众无关、重复、证据不足或没有实质变化。

### 4.4 Content Outcome：真正采用

每周至少有 1 份结果被本人采用为稿件或实际发布；如果没有，必须记录可分析的放弃原因。

## 5. 如何描述“信号”

第一版使用四个彼此独立的维度，避免把来源、主题和验证状态混在一起。

### 5.1 变化类型

- **Capability**：模型或 Agent 新增了什么能力；
- **Tool / Workflow**：某项真实工作开始可以用不同方式完成；
- **Economics / Access**：价格、免费额度、权限、开闭源或部署门槛变化；
- **Ecosystem / Market**：多个产品、协议或工作方式形成结构性变化。

### 5.2 证据类型

- 官方公告、文档、Release、定价页；
- GitHub 代码、Commit、Issue、Discussion；
- 独立报道、论文、测评或安全公告；
- 用户真实体验；
- 本人可复现实测。

`User Reality` 属于证据与验证视角，不与 Capability 等变化类型混为同一轴。

### 5.3 受影响的人与任务

系统必须指向具体的人、任务和情境，不能只写“对普通人有影响”或“AI 很重要”。

### 5.4 编辑状态

使用 `ready_to_write / needs_testing / watch / reject` 表达证据是否足以进入创作，而不是用 Stars、转发量或模糊综合分代替编辑判断。

上述分类是第一版工作假设，应先用 10～20 个真实样例验证，再决定是否固化进数据库 schema。

## 6. 来源的职责

| 来源 | 首要回答的问题 | 不能单独证明 |
| --- | --- | --- |
| Official / Docs / Blog | 正式发布了什么、价格和使用条件是什么 | 实际体验一定好、宣传效果一定成立 |
| GitHub | 开源实现、版本变化、技术边界与 Issue 摩擦 | 大众采用、商业规模、普通人普遍受影响 |
| Web Search | 找到官方原文、独立来源和必要背景 | 搜索摘要本身不是证据，多篇转载不算多源确认 |
| X | 什么刚开始出现、作者和业内人士在讨论什么 | 功能已实现、用户普遍认可 |
| Reddit | 具体使用场景、失败案例、替代方案和用户语言 | 总体市场规模或普遍规律 |
| 本人实测 | 在明确版本与环境下，体验型结论是否成立 | 超出测试范围的普遍结论 |

任何来源都可以发现线索；系统应先找第一方证据确认事件，再根据缺失的证据选择其他来源补齐，而不是在所有平台机械搜索同一个关键词。

## 7. 成功标准

### 产品效果

- 每天输出 0～3 条可在十分钟内处理完的高质量 Signal Card；
- 每周形成 2 份 Dossier；
- 每周至少 1 份进入采用或发布；
- 核心事实均可追溯，官方宣称、社区观点和本人实测不混写；
- 用户能说清每条被采用或拒绝的原因。

### 工程效果

- 采集、去重、证据、状态与反馈可审计；
- 单个来源失败不会让整个流程静默消失；
- 相同事件不会因为跨来源重复出现而生成多份结论；
- 策略变化可版本化、回放和回滚；
- 不读取、记录或输出密钥、Cookie 与个人敏感信息。

工程测试通过只能证明系统可靠，不能代替产品效果验证。

## 8. 第一版明确不做

- 不做全网 AI 新闻聚合器；
- 不做 GitHub 仓库排行榜；
- 不保证爆款、盈利或绝对事实正确；
- 不自动替用户形成最终观点并发布；
- 不同时建设 GitHub、X、Reddit 的全量抓取；
- 不做多用户 SaaS、复杂前端或团队协作；
- 在没有持续反馈样本前，不做在线训练、强化学习或“自动进化”；
- 不让低质量结果为了满足数量目标而进入输出。

## 10. 账号栏目结构（2026-08-16 定稿，DEC-024）

账号定位一句话：**「替普通年轻人翻译这周的 AI（每个数字都可查），并记录我用 AI 给自己造工具的过程」。**

- **主线「这周 AI 关你什么事」**：AI 变化的翻译 + 核验，面向学生，周更；
- **副线「我搭的工具」**：vibecoding 过程向（求职插件、工作台等），面向
  创作者/效率党，每周或双周 1 条，图文为主；
- 两个栏目共用同一信用：真实实盘、数字可查、不搞「最强/必装」安利；
  副线只讲自己真实在用的东西，防止定位漂移。
